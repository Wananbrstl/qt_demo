# 二进制分帧、CRC32 与 CBOR 载荷

## 帧封装

所有整数使用网络字节序：

```text
magic:u32 | version:u16 | type:u16 | flags:u16 | reserved:u16
sequence:u32 | payload-size:u32 | crc32:u32 | payload:N
```

固定 24 字节头让解码器在分配或等待载荷前校验长度。`maximumFrameBytes` 防止损坏或恶意长度字段造成超大内存占用。

解析顺序应为：寻找 magic → 确认头完整 → 读取并验证版本/长度 → 确认整帧完整 → CRC → 解析载荷。长度检查必须防止整数溢出。

## 失步恢复

magic 不在偏移 0 时，解码器向前搜索并报告丢弃字节。找不到完整 magic 时保留最后 3 字节，因为它们可能是跨 TCP 读取边界的 magic 前缀。恢复算法必须保证每轮循环都会消费字节或退出等待，避免恶意输入导致忙循环。

## CRC 范围

CRC 覆盖前 20 字节头和载荷，用于发现偶然损坏并辅助重新同步。CRC 不提供身份真实性，攻击者可以重算 CRC；TLS 与消息认证属于独立安全层。

## CBOR 载荷

CBOR 让外层封装稳定，同时允许消息字段演进。解码器必须验证必填字段、类型和范围，不能假设 map 中总有正确数据。新增字段宜保持旧端可忽略；修改字段语义则应提升协议或消息版本。

## 实验

- 建立协议版本兼容矩阵。
- 在合法帧前插入任意垃圾并验证恢复。
- 构造超过上限及整数边界的长度字段。
- 对输入运行 mutation fuzz：翻转位、截断、重复片段、随机插入。
- 把 Command 的 CBOR 构造收敛为强类型 codec。

验收：AddressSanitizer/UndefinedBehaviorSanitizer 下执行至少 100 万个变异样本，无崩溃、无限循环和越界；错误分类可观测且缓存不超过配置上限。
