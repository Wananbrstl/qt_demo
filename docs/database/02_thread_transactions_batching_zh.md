# 数据库线程、事务与批处理

## 线程亲和性

一个 `QSqlDatabase` 连接必须在同一线程中创建、使用、关闭和移除。`DatabaseWorker::initialize` 在 worker 移入数据库线程后执行，GUI 只通过队列槽发送值类型。连接名应唯一，并在最后一个 query/connection 引用释放后调用 `removeDatabase`。

## WAL 与 busy timeout

WAL 让读者与单写者更有效地共存；busy timeout 可以吸收短暂锁竞争，但不能代替受控事务长度。长读事务可能阻止 checkpoint，导致 WAL 持续增长。应监控 WAL 大小、checkpoint 结果和最长事务时间。

## 批量事务

每条遥测单独做持久事务成本很高。worker 累积 250 ms 后在一个事务中批量写入；失败时把批次放回有界队列前端。批次大小是在吞吐、延迟、锁持有时间和崩溃重做成本之间取舍，不存在脱离负载的固定最优值。

## 失败规则

- 队列上限防止存储故障期间耗尽内存。
- worker 只发出结构化诊断，不直接弹 UI 对话框。
- shutdown 先停止 timer、刷新待写数据、关闭连接，最后移除命名连接。
- 重试必须分类：磁盘满、损坏、约束错误与短暂 busy 不能采用同一策略。
- 队列溢出策略必须明确记录丢弃数量和时间范围。

## 实验

- 把数据库变为只读，观察错误分类和恢复。
- 按小批次删除旧遥测并限制每轮耗时。
- 比较批量 1、10、100、1000 的吞吐与 P99 入库延迟。
- 用独立只读连接承载长查询，比较对写入延迟的影响。
- 在提交前强制终止进程，重启后执行 `PRAGMA integrity_check` 并检查事务原子性。

验收：队列和 WAL 均有上限与指标；GUI 不因数据库慢而冻结；任何失败都能判断数据是已提交、待重试还是已明确丢弃。
