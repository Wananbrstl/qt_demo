# 类设计决策框架

## 1. 核心结论

类设计的第一问题不是“应该使用哪个模式”，而是：

> 这个类型向调用者承诺什么事实，谁负责让这些事实持续成立？

一个类可以看作一组可由编译器、构造过程和封装边界共同维护的承诺。设计模式是
某些承诺组合的常见实现形式，不是推导的起点。

下面的决策过程刻意先处理语义与约束，再处理函数放在哪里、是否虚函数等语法问题。

## 2. 九步决策过程

### 第一步：写一句“对象是什么”

使用名词和可观察语义描述，不要写实现：

- 好：`ImportedFunction<F>` 是一个可以按 `F` 调用、且调用期间模块必然存活的函数；
- 差：`ProcAddress` 保存一个 `HMODULE`、字符串和 `FARPROC`；
- 好：`EntityId` 是数据库实体在一次数据库世代内的稳定身份；
- 差：`EntityId` 是一个 64 位整数包装。

若一句话中出现“有时”“可能尚未”“调用某函数后才”，说明它很可能包含多个状态，
需要继续决定这些状态是对象的本质，还是应该拆成不同类型。

### 第二步：判定语义类别

| 类别 | 判断问题 | 默认设计倾向 |
|---|---|---|
| 值 | 两个内容相同的实例是否可互换？ | 可复制、比较、无外部身份 |
| 实体 | 即使属性相同，两个实例是否仍不同？ | 稳定 ID，限制复制 |
| 拥有型资源 | 析构是否必须执行释放动作？ | RAII、移动或共享所有权 |
| 借用/视图 | 数据是否由别处拥有？ | 小型按值传递，不长期保存 |
| 描述 | 它是否只表达意图，尚未执行？ | 纯数据、易验证、易序列化 |
| 已编译/已解析对象 | 是否保证可以执行？ | 工厂创建、强不变量 |
| 服务/协调器 | 是否协调多个外部对象？ | 缩小状态，显式依赖注入 |

CAD 中最常见的误判，是把数据库实体当值复制，或把事务内借用指针当长期实体引用。

### 第三步：列出不变量

先列出必须始终成立的事实，再写成员：

```text
ImportedFunction<F>
  1. 函数地址非空；
  2. 地址与 F 的 ABI 契约匹配（由调用方声明和插件协议共同保证）；
  3. 地址被调用期间，包含它的模块不会卸载。
```

成员只是实现这些事实的一种方式。本示例使用“类型化函数指针 + 共享模块状态”实现
第 1 和第 3 项；第 2 项无法由 `GetProcAddress` 反射验证，必须由版本化 C ABI 保证。

### 第四步：画状态机

至少列出：创建前、有效、移动后、失败、关闭/卸载后。如果一个公共成员函数需要反复
检查 `initialized_`、`valid_`、`resolved_`，通常有三种可能：

1. 这个状态机确实是领域概念，应显式建模；
2. “描述”和“已解析结果”应拆成两个类型；
3. 对象本应由工厂一次性构造为有效状态。

不要仅为避免异常而默认采用两阶段初始化。它把一次失败变成所有成员函数的长期前置条件。

### 第五步：建立所有权图

为每一条指针、引用、句柄和 view 写出：

- 谁创建；
- 谁释放；
- 能否共享；
- 被引用者是否可能提前失效；
- 跨线程和跨 DLL 边界是否有效。

所有权不是 `unique_ptr`/`shared_ptr` 的选型题，而是生命周期图。只有当“最后一个使用者
销毁资源”符合领域语义时才使用共享所有权。本项目中的已解析函数需要延长 DLL 生命周期，
因此共享控制块有明确语义；普通 CAD 图元不应因此普遍改为 `shared_ptr`。

### 第六步：确定失败分类和承载层级

先区分：

- 编程错误：违反内部契约、索引错误、不可达状态；
- 可恢复环境错误：文件缺失、DLL 或符号缺失、输入格式错误；
- 领域拒绝：事务冲突、约束不一致、对象已被删除；
- 进程级故障：内存耗尽、核心数据库损坏。

再决定异常、`Result<T>`、错误码或终止策略。缺少 DLL/符号是环境错误，因此示例使用
`Result<T>`。LLVM 的 `Expected<T>` 同样用于“可能失败且还要返回值”的函数，并明确建议
fallible constructor 使用命名工厂，避免把无效对象交给调用者。

### 第七步：决定时间语义

eager/lazy 不是性能偏好，而是可观察语义：

| 问题 | 倾向 eager | 倾向 lazy |
|---|---|---|
| 结果是否是对象身份的一部分？ | 是 | 否 |
| 失败是否应在装配阶段集中报告？ | 是 | 否 |
| 操作是否几乎总会发生？ | 是 | 否 |
| 外部状态是否希望在每次使用时重新观察？ | 否 | 是 |
| lazy 是否引入锁、缓存和隐式可变性？ | 是 | 代价可接受时 |

若选择 lazy，必须定义缓存、重试、并发和外部状态变化的语义，不能只写一个
`mutable optional<T>` 就结束设计。

### 第八步：管理依赖方向与扩展点

先问“哪一部分更稳定”。稳定策略不应依赖具体插件；领域模型不应依赖 UI；几何内核不应
依赖命令注册。扩展点可选用函数对象、模板、类型擦除、C ABI 工厂或虚接口，但选择标准是
依赖方向、部署边界和变化频率，而非个人偏爱的模式。

### 第九步：以误用和变化场景审查

至少演练：

1. 调用者漏掉一步会怎样？
2. 资源提前销毁会怎样？
3. 新增状态、错误或插件版本会改多少调用端？
4. 类型能否被放进容器、跨线程或跨 DLL？
5. 测试是否必须启动完整 CAD 宿主？
6. 热路径的布局、分配和间接调用是否经过测量？

## 3. 构造函数决策准则

构造函数的职责不是“只能赋值”，而是建立类型承诺。建议按以下顺序选择：

1. 初始化不会按正常业务条件失败：直接构造；
2. 失败是异常策略所接受的异常：构造中 RAII 获取，失败抛出；
3. 失败是常见且调用者要分支处理：私有构造 + `create/load/compile` 返回 `Result<T>`；
4. “未解析”本身是有用领域状态：建立独立描述类型，并提供 `resolve()`；
5. 对象确实需要反复打开/关闭：显式状态机，不伪装成永远有效的值。

C++ Core Guidelines 的 C.40/C.41 要求构造建立不变量和完整对象；C.42 在异常可用时建议
构造失败抛出。LLVM 在不采用异常的代码库中用命名工厂和 `Expected<T>` 达到同一个上层目标：
调用者得到“有效对象或错误”，而不是需要记得调用 `isValid()` 的半成品。

## 4. 类边界的实用准则

### 应优先做

- 用领域名称表达语义差异，如 `SymbolRequest` 与 `ImportedFunction`；
- 输入 view、内部拥有：短调用可接受 `string_view`，若需保存则复制为 `string`；
- 把平台强制的 cast、宏和句柄限制在一个窄边界；
- 让值类型遵守正常复制含义，让资源类型明确移动/共享含义；
- 返回包含上下文的结构化错误；
- 对声明先验证并编译，再进入高频执行路径；
- 用基准数据决定小对象优化、arena 和容器替换。

### 需要警惕

- `init()` 后才能使用，但类型没有表达这一前置条件；
- getter 暴露可变容器并绕过不变量；
- 所有类都继承同一 `Object` 基类；
- 为测试访问 private 实现，而不是拆出可测试职责；
- 以 `shared_ptr` 消除所有生命周期思考；
- 配置文件以字符串重建一套没有验证器的弱类型系统；
- 在 DLL 边界传递 STL 对象、异常或由另一侧释放的内存，却没有统一工具链和 ABI 策略。

## 5. 代码审查清单

- [ ] 类型的一句话语义是否不依赖成员实现？
- [ ] 值、实体、资源、视图、描述和服务是否区分清楚？
- [ ] 构造后不变量是否可写成清晰列表？
- [ ] 无效状态能否被拆成错误结果或另一类型？
- [ ] 每个句柄和 view 的 owner 是否明确？
- [ ] 返回的指针/view 是否有可陈述的生命周期上界？
- [ ] 失败属于哪个层级，调用者真的能处理吗？
- [ ] lazy 的缓存、重试和线程语义是否明确？
- [ ] ABI、线程和事务边界是否反映在接口中？
- [ ] 扩展点是否指向较稳定的抽象？
- [ ] 性能选择是否有规模假设或测量？
- [ ] 单元测试能否不启动完整宿主？
