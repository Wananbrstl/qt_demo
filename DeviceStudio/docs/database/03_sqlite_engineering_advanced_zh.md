# 工业上位机 SQLite 进阶：模式、性能与故障恢复

本文讨论单机上位机中 SQLite 的工程化使用。SQLite 无需独立服务，但它仍是事务数据库；线程、事务、索引、WAL 和磁盘故障都必须被显式设计。内容映射到 `DatabaseWorker`、`001_initial.sql` 和数据库集成测试。

## 1. 从访问模式设计数据模型

先列出读写路径和服务目标，再画表：

```text
写：每设备持续追加遥测，偶尔写命令与告警
读：按设备和时间倒序分页；按时间范围聚合
运维：按保留期删除；迁移；备份；完整性检查
目标：写入不阻塞 UI，历史查询 P99 可控，磁盘占用有上限
```

设备 ID 应稳定且与显示名称分离。时间序列主查询由 `(device_id, captured_at_ms)` 驱动；若同一毫秒允许多条记录，必须用 `id` 作为稳定次排序键。

需要主动决定单位和语义：时间用 UTC epoch 毫秒还是纳秒，温度是否允许 NULL，质量码如何表达，设备时钟和上位机接收时间是否同时保存。模糊语义比字段类型错误更难修复。

## 2. B-tree 与复合索引算法

SQLite 普通索引使用 B-tree。查找大致为 `O(log N)`，但真实成本取决于页访问、缓存命中、结果行数和回表次数。复合索引遵循最左前缀：索引 `(device_id, captured_at_ms DESC, id DESC)` 可以支持指定设备后的时间范围与排序。

索引设计步骤：

1. 写出高频 SQL 的 WHERE、ORDER BY 和返回列。
2. 把等值过滤列放在范围列之前。
3. 让索引顺序尽量满足排序，避免临时 B-tree。
4. 使用 `EXPLAIN QUERY PLAN` 验证，不凭命名猜测。
5. 用接近生产的数据量和分布测量分位延迟。

覆盖索引可以减少回表，但增加索引宽度、磁盘和写放大。上位机遥测通常写多读多，不能为每一种 UI 排序都建索引。

## 3. 查询计划与统计信息

`EXPLAIN QUERY PLAN` 应检查：是否 SEARCH 而非全表 SCAN，使用哪个索引，是否出现 `USE TEMP B-TREE FOR ORDER BY`。执行 `ANALYZE` 后，优化器可依据统计信息选择计划；数据分布大幅改变时需要重新分析。

参数化 SQL 的实际选择性可能不同。测试至少覆盖：单设备高密度、设备很多但每台稀疏、短时间窗无数据、长时间窗大量数据。

不要只测平均值。历史查询卡顿通常由长尾产生，应记录 P50/P95/P99、返回行数、扫描计划和 GUI 投递耗时。

## 4. 事务与批量写入

SQLite 同一时刻只有一个 writer。单条事务频繁 fsync，吞吐差；超大事务又会延长锁持有和崩溃恢复。批量大小需要在吞吐与入库延迟间平衡。

设到达率为 `λ`、固定事务成本为 `C`、单行成本为 `r`、批量为 `B`，粗略平均每行成本可表示为 `C/B + r`。B 增大时收益递减，而等待凑批和锁时间增加。

可实现双阈值批处理：达到 `maxBatchRows` 或 `maxBatchDelay` 任一条件就提交。进一步根据队列水位自适应：低负载优先低延迟，高负载扩大批次，但必须设置硬上限。

失败分类：

- `SQLITE_BUSY/LOCKED`：短暂竞争，可有界退避重试。
- `SQLITE_FULL`：磁盘满，继续重试只会扩大内存队列。
- 约束错误：通常是数据或程序缺陷，应隔离坏记录。
- `CORRUPT/NOTADB`：停止写入并进入恢复流程。
- IO 错误：记录底层错误，避免无限快速重试。

## 5. WAL、checkpoint 与读写并发

WAL 模式下，writer 追加 WAL，reader 读取稳定快照。reader 不等于没有成本：长期读事务会阻止 checkpoint 推进，WAL 可能无限增长。

需要掌握：

- passive checkpoint 尽量不阻塞；restart/truncate 更积极但可能等待 reader。
- 自动 checkpoint 的页数阈值不是字节数或时间。
- `busy_timeout` 只处理短竞争，不应掩盖长事务。
- 单独只读连接能隔离 query 对 writer 的连接占用，但仍共享文件锁与 WAL。

监控 WAL 文件字节数、checkpoint 的 busy/log/checkpointed 页数、最长读事务和写提交 P99。给 WAL 制定告警阈值与恢复动作。

## 6. Qt SQL 线程与生命周期

`QSqlDatabase` 是连接句柄，不是可以在线程间自由共享的普通值。连接应在使用线程创建和销毁；`QSqlQuery` 也不得跨线程。推荐命令式边界：GUI 发值类型请求，数据库 worker 在线程内执行，结果以值类型返回。

关闭顺序：

1. 拒绝新请求。
2. 停止批处理 timer。
3. 有界刷新或明确标记未写数据。
4. 销毁所有 query。
5. close 并清空 `QSqlDatabase` 句柄。
6. `removeDatabase(connectionName)`。
7. 退出线程。

测试应捕获 Qt 的“connection is still in use”警告，不能把它视为无害日志。

## 7. 迁移算法与可恢复升级

迁移是按版本排序的不可变操作序列。启动算法：

1. 打开数据库并读取 schema version。
2. 若数据库版本高于程序支持版本，拒绝写入。
3. 验证待执行迁移连续且未被篡改，可选保存 checksum。
4. 每个迁移在事务中执行；成功后原子更新版本。
5. 失败回滚并保留足够诊断，不允许服务“半启动”。

大表变更可能无法在一次短事务完成。SQLite 常用“新表 → 分批复制 → 校验 → 切换”的策略；操作前应备份并评估额外磁盘。迁移必须同时测试“全新建库”和“每个受支持旧版本逐级升级”。

## 8. 键集分页算法

OFFSET 分页越往后通常扫描越多，而且并发插入会改变位置。对倒序 `(captured_at_ms, id)` 使用游标：

```sql
SELECT ...
FROM telemetry_samples
WHERE device_id = ?
  AND (captured_at_ms < ?
       OR (captured_at_ms = ? AND id < ?))
ORDER BY captured_at_ms DESC, id DESC
LIMIT ?;
```

下一页使用上一页最后一行的 `(captured_at_ms, id)`。复合排序键保证相同时间戳下无遗漏。游标应包含查询过滤条件或签名，防止被错误复用到另一设备。

## 9. 保留策略与有界删除

直接删除数百万行会形成长事务、扩大 WAL 并阻塞其他写入。使用小批次循环：按索引选择一批主键，删除后提交，检查是否需要让出事件循环。批次大小由单批耗时和写入影响决定。

删除后数据库文件通常不会自动缩小。`VACUUM` 需要额外空间且可能长时间独占，不适合无计划运行。可评估 `auto_vacuum=INCREMENTAL`，但必须从数据库创建阶段规划并测量碎片与写放大。

保留策略要明确：按设备时间、全局磁盘水位，还是两者结合；磁盘临界时是停止采集、删除最旧数据还是告警等待人工处理。安全和合规数据不能仅按“最旧”删除。

## 10. 时间序列聚合算法

UI 不应为绘制一天曲线加载每个原始点。可按固定时间桶聚合 count/min/max/avg。平均值长期累加宜使用 Welford 在线算法维护均值和方差，数值稳定性优于“平方和减均值平方”。

曲线降采样可学习 Largest-Triangle-Three-Buckets（LTTB），它比简单每 N 点抽样更能保留视觉峰谷。但用于告警和统计时必须保留原始数据或明确聚合语义，视觉算法不能替代业务计算。

聚合表的更新策略有三种：写入时同步、后台异步、查询时临时计算。同步增加写成本；异步存在短暂滞后；临时计算增加查询长尾。选择必须由数据量和新鲜度 SLA 驱动。

## 11. 完整性、备份与恢复

备份运行中的 WAL 数据库时，不要只复制 `.db` 文件。使用 SQLite Online Backup API、`VACUUM INTO` 或受控 checkpoint/停机方案。恢复演练比“已经有备份文件”更重要。

建议分层检查：

- 启动快速检查：版本、关键表/索引、可写空间。
- 周期维护：`PRAGMA quick_check`。
- 故障调查：`PRAGMA integrity_check`，评估运行成本。
- 应用一致性：孤儿外键、时间范围、重复请求 ID、聚合与原始数据对账。

安全策略包括数据库目录权限、敏感字段加密需求、日志脱敏和备份访问控制。SQLite 文件容易复制，这既是部署优势也是数据泄露风险。

## 12. 进阶实验

### 实验 A：索引与查询计划

步骤：生成至少 1000 万条、100 台设备的偏斜数据；比较无索引、单列索引、复合索引和覆盖索引。

指标：数据库/索引大小、插入吞吐、查询 P50/P95/P99、query plan。

通过标准：能用查询形状解释最优索引；不是单纯选择查询最快但写入和空间不可接受的方案。

### 实验 B：批量大小与耐久性

步骤：批量取 1/10/100/1000，分别测试正常负载与突发负载；在事务提交前后随机杀进程。

指标：每秒写入、入库延迟分位、队列高水位、重启恢复时间、丢失/重复行。

通过标准：事务内全有或全无；选定批量满足延迟与吞吐目标，队列有界。

### 实验 C：WAL 被长 reader 阻塞

步骤：开启长读事务，同时持续写入并周期 checkpoint，然后释放 reader。

指标：WAL 大小、checkpoint busy 页、写 P99、释放后的回收时间。

通过标准：监控能在磁盘风险前告警；释放 reader 后 WAL 回到阈值；GUI 不冻结。

### 实验 D：键集与 OFFSET 分页

步骤：从深页开始查询，同时持续插入相同时间戳数据；比较两种分页。

指标：每页耗时随深度变化、重复/遗漏数量、计划。

通过标准：键集分页延迟近似稳定且无重复遗漏；排序键和游标语义有自动化测试。

### 实验 E：在线迁移失败恢复

步骤：从真实旧版本副本执行 `002`，在每个关键步骤注入磁盘满、SQL 错误和进程终止。

指标：最终 schema version、表结构、数据行数、可再次启动性。

通过标准：结果只能是完整旧版本或完整新版本，不存在程序继续写入半迁移结构。

### 实验 F：保留与磁盘压力

步骤：限制虚拟磁盘容量，持续写入并执行小批次保留；模拟删除跟不上写入。

指标：磁盘余量、删除/写入速率、WAL 峰值、单批耗时、丢弃策略触发次数。

通过标准：磁盘不会无告警耗尽；系统按文档策略降级，丢弃数据范围可追踪。

### 实验 G：备份恢复演练

步骤：在持续采集期间生成备份，在全新目录恢复，运行迁移、完整性检查和业务对账。

指标：恢复点目标 RPO、恢复时间 RTO、行数/校验和差异。

通过标准：在目标 RPO/RTO 内恢复；不仅文件可打开，而且历史查询、外键和 schema version 全部正确。

## 13. 完成检查表

- 模式来自读写路径与数据语义，而不是 UI 表格列。
- 每个关键 SQL 都有真实规模的 query plan 与分位延迟证据。
- 写入队列、事务、WAL、保留和磁盘均有上限。
- Qt SQL 连接不跨线程，关闭顺序可测试。
- 迁移不可变、可重放、失败可回滚，新库与升级库结构一致。
- 深分页使用稳定键集，时间序列聚合不会伪造业务精度。
- 备份已经实际恢复并通过应用级校验。

达到这些条件，才是一个可长期运行、可升级、可诊断的上位机本地存储子系统。
