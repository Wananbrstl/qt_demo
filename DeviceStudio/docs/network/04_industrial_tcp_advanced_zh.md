# 工业上位机 TCP 进阶：从可连接到可证明可靠

本文面向已经会使用 `QTcpSocket` 的 C++/Qt 开发者。目标不是再写一个 echo demo，而是建立可以评审、测试和运维的通信模型。学习时应把每个概念映射到 `DeviceSession`、`FrameCodec`、`DeviceSimulator` 和 Protocol Inspector。

## 1. 先定义服务语义，再选择 API

上位机通信至少包含四层责任：

```text
传输层：TCP 连接、有序字节、流量控制
成帧层：边界、长度、校验、版本、最大资源消耗
会话层：握手、心跳、重连、请求关联、连接代次
业务层：命令权限、幂等、状态一致性、超时后的处置
```

TCP 的“可靠”只表示一个连接内按序重传字节。它不保证：

- 一次 `write` 对应一次接收回调；
- 应用消息已被业务处理；
- 断线前最后一条命令没有执行或只执行一次；
- 重连后旧响应不会污染新会话；
- 对端身份可信或数据保密。

设计评审必须先写清楚业务交付语义：允许至多一次、至少一次，还是通过幂等键逼近恰好一次。对于“启动主轴”这类有副作用命令，超时不是简单的失败，而是“执行状态未知”。

## 2. 流式解析算法与资源上限

### 2.1 增量解析不变量

一个正确的增量 decoder 应保持以下不变量：

1. 缓冲区只保存尚未消费的字节。
2. 不完整头或载荷只会等待，不会越界读取。
3. 声明长度在加法和类型转换前完成上限校验。
4. 每次解析循环要么消费至少一个字节，要么退出等待更多数据。
5. 任意输入下，内存和单次处理时间都有上限。

当前 magic 搜索适合短固定标记。若标记更长、噪声输入多，可学习 KMP 的前缀函数，使扫描复杂度保持 `O(n+m)`，避免朴素回退造成重复比较。对于固定 4 字节 magic，`QByteArray::indexOf` 足够，真正重要的是失步后的保留规则和最大缓存。

### 2.2 缓冲结构选择

- `QByteArray + remove(0,n)` 简单，但频繁头删可能移动内存。
- “QByteArray + readOffset” 可摊销移动成本，超过阈值再 compact。
- 环形缓冲区能稳定复用内存，但跨尾部读取和查找更复杂。

不要只依据理论复杂度替换结构。先用典型帧长、吞吐和拆分模式测量 CPU、分配次数与峰值内存。

### 2.3 CRC32 的定位

CRC32 适合发现随机位错误，查表实现可把逐位算法从每字节 8 轮降为 1 次表查找。更高吞吐可以使用 slicing-by-8 或硬件指令，但必须用固定测试向量验证多实现一致性。CRC 不是 MAC，不能阻止恶意篡改；安全需求应使用 TLS，并在必要时增加消息级签名或 HMAC。

## 3. 显式有限状态机

建议把状态机写成“状态 × 事件 → 动作/新状态”表，而不是让 socket 回调随意修改多个布尔量。主要事件包括：

- 用户 Connect/Disconnect；
- TCP Connected/Disconnected/Error；
- HelloAck、合法业务帧、协议错误；
- HandshakeTimeout、HeartbeatTick、SilenceTimeout、ReconnectTimer；
- 应用 Shutdown。

需要特别定义的规则：

- `HelloAck` 只接受于 Handshaking，其他状态收到要记录异常。
- 每次 TCP 建连生成递增 connection generation；异步响应必须携带或关联代次。
- 用户断开和网络故障是不同事件，前者禁止自动重连。
- shutdown 应幂等，多次调用结果相同。

状态机测试不应依赖真实秒数。把时钟与随机数作为依赖注入，使用虚拟时间枚举事件序列。进一步可做 model-based testing：由参考状态表生成随机事件，比较实际状态和模型状态。

## 4. 心跳、超时与 RTT

心跳间隔不能简单设置得越短越好。短间隔增加带宽、唤醒和误判；长间隔增加故障发现时间。需要结合控制周期、网络抖动、设备处理上限和允许恢复时间决定。

掌握以下算法：

- 单调时钟：间隔测量使用 monotonic time，不使用可能跳变的墙上时间。
- EWMA：`SRTT = (1-α)·SRTT + α·RTT_sample`，平滑往返时延。
- 偏差估计：维护 RTT variation，超时阈值使用 `SRTT + K·RTTVAR` 并设置上下界。
- φ accrual failure detector：把到达间隔转为怀疑度，适合延迟分布变化明显的系统；使用前必须验证误报率，不能为了算法复杂而复杂。

本工程固定 2 秒/6 秒适合作为教学基线。进阶实验应先收集分布再调整，而不是凭直觉改常量。

## 5. 指数退避与随机抖动

无抖动退避 `min(cap, base·2^attempt)` 会让同一时刻掉线的客户端继续同步。常见策略：

- Full jitter：在 `[0, exponential_cap]` 均匀随机。
- Equal jitter：`cap/2 + random(0, cap/2)`。
- Decorrelated jitter：基于上次延迟随机增长，再受全局上限约束。

算法必须处理指数溢出：先限制 attempt 或使用饱和乘法。成功建连后不要立刻清零，可在稳定在线一段时间后重置，避免抖动链路持续快速重试。

## 6. 背压、队列与调度

必须为每个队列定义：容量、计量单位、满载策略、生产者是否可阻塞、丢弃是否允许、指标和告警。

典型分类：

- 控制命令：数量少但不能静默丢弃；满载时拒绝新命令并返回明确错误。
- 实时遥测：通常允许合并或覆盖旧值，保证“新鲜度”比完整性重要。
- 历史上传：可批量且需要公平调度，不能饿死控制命令。

可采用有界优先队列或加权轮询。纯优先队列可能让低优先级永久饥饿；weighted round-robin 或 deficit round-robin 更适合不同大小消息。监控 `bytesToWrite()` 只能看到 Qt/socket 层，还应监控应用队列的条目数、字节数、最老等待时间和丢弃数。

Little 定律 `L = λW` 可用于一致性检查：平均到达率 λ 和平均等待时间 W 对应平均队列长度 L。若测量严重不符，通常说明统计窗口、丢弃或重试计数有误。

## 7. 请求关联、超时与幂等

为命令分配全局唯一 `requestId`，维护有界 pending map：

```text
requestId -> {connectionGeneration, deadline, retryPolicy, completion}
```

超时管理可从逐请求 timer 演进为最小堆：堆顶是最近 deadline，插入/删除 `O(log n)`。大量相近超时时间也可使用时间轮，以近似 `O(1)` 处理。无论选择什么结构，都要限制 pending 数量，并在断线时按策略完成、保留或转为未知状态。

幂等设计示例：

- “把速度设置为 1000”天然比“速度增加 100”更容易幂等。
- 设备保存最近请求 ID 与结果，重复 ID 直接返回原结果。
- 请求记录必须有保留期限和容量，重启后是否保留取决于风险。
- 客户端收到未知、过期或旧连接代次响应时记录并丢弃。

所谓“恰好一次”通常是传输重试、持久去重和业务幂等共同产生的效果，不是 TCP 的属性。

## 8. 多设备架构与线程模型

不要机械地为每台设备创建一个线程。事件驱动 socket 可以在一个网络线程管理多个连接；CPU 密集的编解码或加密再交给受限线程池。选择时测量：连接数、每秒帧数、单帧 CPU、最大可接受事件循环延迟。

关键规则：

- socket 只能在亲和线程操作；
- GUI 只接收降频或聚合后的值；
- 队列连接不是自动背压，事件队列也可能无限增长；
- 关闭顺序要停止新请求、结束 socket/timer、清空或失败 pending，再退出线程。

## 9. 可观测性与安全基线

每条连接日志至少包含 deviceId、connectionGeneration、状态、原因、远端、协议版本和时间。指标至少包含：

- 在线连接数、建连成功率、握手/重连耗时；
- 入站/出站帧率与字节率；
- CRC/协议/版本错误计数；
- 队列当前值和高水位、丢弃数；
- 请求成功、超时、未知状态及 P50/P95/P99 延迟；
- 心跳 RTT 与连续丢失次数。

日志不得记录密钥和敏感生产参数。生产网络应评估 TLS、证书轮换、双向认证、命令授权、防重放和速率限制。网络隔离不是身份认证。

## 10. 进阶实验

### 实验 A：分帧属性测试与 fuzz

步骤：生成合法帧序列，随机拆分/合并；再做翻转、截断、插入、长度畸变。使用 ASan/UBSan 运行至少 100 万例。

指标：解析成功帧、错误分类、最大缓存、单输入最长时间、崩溃数。

通过标准：合法序列无丢失和重复；畸形输入不越界、不死循环，缓存不超过上限。

### 实验 B：100 客户端重连风暴

步骤：同时断开 100 个客户端，比较无抖动、full jitter、decorrelated jitter；固定随机种子重复 30 次。

指标：每 100 ms 建连尝试数、峰值、恢复 P95、服务器 CPU。

通过标准：抖动后峰值显著下降，所有客户端在上限时间内恢复，主动断开的客户端为零重试。

### 实验 C：慢消费者与背压

步骤：限制接收端读取速率，持续发送遥测并穿插控制命令。

指标：应用队列/Qt 写缓冲高水位、命令 P99、遥测丢弃或合并数、内存。

通过标准：内存稳定有界；控制命令不被遥测饿死；丢弃行为与文档策略一致且可观测。

### 实验 D：命令超时的未知状态

步骤：设备执行命令后、发送响应前断线；客户端重连并按不同策略重试。

指标：设备实际执行次数、客户端最终状态、重复响应、人工介入次数。

通过标准：幂等命令最多产生一个最终效果；非幂等命令不会被无条件自动重发，UI 明确显示“执行状态未知”。

### 实验 E：自适应心跳

步骤：注入 20～500 ms 延迟和周期性 2 秒尖峰，比较固定超时与基于 SRTT/RTTVAR 的阈值。

指标：故障发现时间、误断线率、重连次数。

通过标准：在预定故障发现 SLA 内显著降低误断线；上下界保证阈值不会无限增长。

### 实验 F：端到端故障演练

步骤：运行 8 小时，随机执行断网、服务重启、半开连接、畸形帧和数据库慢写。

指标：数据缺口、重复命令、恢复时间、队列/WAL 峰值、GUI 最大卡顿。

通过标准：所有资源有界；故障能从日志和指标还原；安全相关命令没有未解释的重复执行。

## 11. 完成检查表

- 能从 TCP 语义推导应用帧和确认协议，而不是依赖 readyRead 经验。
- decoder 对任意输入在空间和时间上有界。
- 状态机、时钟和随机数可测试。
- 所有发送、pending 和事件队列都有容量与满载策略。
- 超时、重试、幂等和连接代次共同定义清晰的命令语义。
- 有分位延迟、队列高水位和恢复时间数据，不只报告“测试通过”。

达到这些条件，才从“会用 QTcpSocket”进入“能设计和验证工业通信子系统”。
